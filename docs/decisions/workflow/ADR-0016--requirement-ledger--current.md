# ADR-0016 · 요구는 요구사항 목록 하나를 단일 원천으로 삼는다

- 맥락: 사용자가 "글자 수는 상관없다"고 지시했는데도 3,000~4,000자 상한이 수정 해석과 분량 가드에 그대로 남았다(2026-11-17 실측).
- 원인(SSoT·SOLID):
  - 요구가 `idea`·`direction`·`feedback`·`brief.acceptance`·`requirements()`에 흩어져 있었고 현재 유효한 값을 정하는 곳이 없었다.
  - 분량 검사(`required`)가 원천 우선순위까지 함께 맡고 있었다(SRP 위반).
  - 의뢰 값이 언제나 최우선 순위를 차지했고, "해제"를 나타낼 수단이 없었다.
  - 새 요구 종류가 늘 때마다 원천 사슬과 프롬프트를 함께 고쳐야 했고(OCP 위반), 프롬프트 신뢰 경계도 모든 원천을 같은 비중으로 늘어놓았다.
- 대안:
  - 분량 항목을 세 상태로 두는 방안은 분량 문제만 풀 뿐 같은 구조적 한계가 남는다.
  - 프롬프트에 우선순위 문구만 추가하는 방안은 코드 가드와 어긋난다.
  - 요구사항 목록을 두는 방안을 택하였다.
- 선택: 요구사항 목록을 사용한다(이벤트를 기록한 뒤 항목별 최신 값으로 집약한다).
  - 기록: `state.requirementLog[]`에 `{revision, source(form|idea|feedback), changes[{kind, op(set|lift), value?, quote}]}` 형식으로 기록한다. 이를 집약한 결과인 `standing(state)`가 유일한 "지금 유효한 요구"가 된다.
  - 기록 주체: 의뢰 화면과 CLI 선택값(코드, form), 글감 문장(진단 AI, idea, 1회), 사람 피드백(수정 해석 AI, feedback, 해석 승인 시 반영)에서만 기록하고, 자동 보정 지시는 적지 않는다.
  - 뜻 해석은 LLM이 맡고(“상관없다” → lift), 사람은 해석 확인 단계(ADR-0010)에서 변경분을 검토한다(JUDGE-001).
  - 요구 종류는 `contracts/requirements.mjs`(값 형식·표시)에 등록하고, 코드 검사는 `domain/requirements.mjs`의 `CHECKS`에 종류별 전략을 등록해 처리한다. 검사기가 없는 종류는 검토 점검표 R로 확인한다.
  - 프롬프트: `requirements`(요구사항 목록)가 유일한 요구이며, 원문(idea·feedback)은 배경 정보로 둔다. 두 내용이 충돌하면 요구사항 목록을 우선한다.
  - 이전 상태: 요구사항 목록이 없는 기존 글은 첫 전이 때 이전 규칙(의뢰 값 → 수정 해석 분량 → 피드백·글감 문장 순서)으로 1회 생성한다(`domain/legacy-requirements.mjs`).
- 결과: 새 요구 종류를 추가할 때 등록 1건(셀 수 있는 경우에는 검사기 1건 추가)만으로 확장할 수 있다. 분량 전용 분기와 문장 정규식 파싱은 이전 글 변환에만 남기고 제거하였다. 진단과 화면의 서술 방식·독자 수준도 요구사항 목록 값을 우선한다.
- 대체: ADR-0007의 "요구 원천" 항목을 대체한다.
- 관련: ADR-0007, ADR-0008, ADR-0010, JUDGE-001
