# ADR-0008 · AIN 내부 편집장의 수정 해석과 합격 판정

- 맥락:
  - 첫 모델이 모호한 피드백을 글자 그대로 처리하다가 문제가 생겼다(예: "너무 길어" 요청에 초고만 줄이려다 8천 자를 다시 쓰면서 시간 초과가 났다).
  - 기존에는 편집장이 대화 중 외부 에이전트일 때만 동작하였다(ADR-0006).
  - 과제별 규칙을 늘리는 방식은 특정 요청에만 맞춰지는 한계가 있다.
- 근거: RES-006이 정리한 실제 편집 협업(편집 메모, 편집 수준, 합격 기준)을 바탕으로 한다.
- 선택:
  - 요청 해석: 수정 위치 판단(route)을 수정 해석으로 확장하여 `{reason=의도, target, level, priorities, preserve, assumptions, acceptance{length, criteria}}` 구조로 상태 `brief`에 기록한다.
  - 범위: 편집 수준에 따라 복귀 단계를 결정적으로 보정한다(`levelTarget`). `developmental`은 늦어도 `outline`으로, `line`과 `copy`는 `draft`로 보정한다.
  - 합격 판정: review 단계는 수정 해석을 기준으로 `verdict`(pass|revise), `reviseFrom`, `unmetCriteria`를 판정한다. 이를 코드 가드(ADR-0007)와 같은 미충족 형식으로 합쳐 자동 재작성 상한 2회까지 진행한다.
  - 표시: 화면과 CLI에 "수정 해석"(의도, 우선순위, 살릴 것, 가정)을 표시한다. 사람 피드백은 승인을 받은 뒤 착수한다(ADR-0010).
- 이유:
  - 대화 여부와 관계없이 같은 품질 루프를 적용할 수 있다.
  - 범용 양식이므로 요청 종류(분량, 톤, 구조)에 영향을 받지 않는다.
  - 수정 회차마다 추가 AI 호출이 들지 않는다(route 단계를 확장해 처리한다).
- ADR-0006 변경: 외부 에이전트는 루프의 필수 단계가 아니며, 사람과 같은 경로로 요청하는 조언자 역할을 맡는다. 최종 검수는 계속 사람이 한다.
- 관련: ADR-0007, FLOW-002, RES-006
