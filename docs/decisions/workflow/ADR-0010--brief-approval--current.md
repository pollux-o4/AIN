# ADR-0010 · 사람 수정 요청은 수정 해석을 승인한 뒤 착수한다

- 맥락: ADR-0008의 수정 해석이 만들어지자마자 바로 수정 루프로 들어가, 잘못된 해석(예: "구성은 그대로"라는 요청인데도 구성부터 다시 쓰는 경우)을 긴 초고 루프와 비용이 든 뒤에야 발견하였다.
- 근거: RES-006의 실제 편집 협업에서는 편집 메모(edit letter)를 저자와 합의한 뒤 작업을 진행한다.
- 선택:
  - 상태 `awaiting_brief`: 사람 피드백이 들어오면 route 단계에서 수정 해석을 제안하고 사람 확인을 기다린다. 기다리는 동안 산출물은 바꾸지 않는다(waiting_route와 같은 계약이다).
  - 사람 동작: `approve_brief`는 그대로 승인하거나 `edit{intent,target,priorities,preserve}`만 보정하여 승인 대상 단계부터 수정을 진행한다. `revise_brief`는 보정 의견을 피드백에 덧붙여 route를 다시 요청한다.
  - 승인 이후의 자동 보정(ADR-0007)은 승인된 수정 해석 범위 안에서 추가 승인 없이 진행한다.
  - 편집장(에이전트)이 내린 수정 지시는 지시자가 해석을 확정한다(`briefPreapproved`). 사람 지시의 해석 승인과 재해석은 사람이 직접 하거나 편집장이 대리한다(2026-11-11 사용자 결정에 따라 편집장이 해석을 검토·확정해 진행하며, 재해석은 수정 지시 한도에 포함한다).
  - 표시: 화면에는 "수정 해석 확인"(편집 가능 양식, 가정 표시, "이대로 진행"·"고친 해석으로 진행"·"다시 해석")을 표시한다. CLI는 `approve-brief`와 `revise-brief`를 사용하며, `can.approveBrief`를 제공한다.
- 이유: 해석은 약 15초면 끝나는 짧은 호출이지만, 초고 루프는 몇 분이 걸리고 비용도 크다. 비용이 들기 전에 의도를 맞추고, 과제별 규칙 없이도 사람이 피드백 문구 해석을 바로잡을 수 있다.
- 비용: 사람 피드백마다 확인 1회가 늘어난다.
- 관련: ADR-0006, ADR-0007, ADR-0008, FLOW-002, RES-006, e2e BRIEF-001
