# JUDGE-001 · 글 품질 판정 경계: 코드는 세고 대조하고, 뜻은 검토(LLM)가 판정

- 범위: 산출물(구성·초고)의 품질 판정과 그 근거 자료 · 검토 입력 지표(`paseo/metrics`) · 코드 가드(`editorial/domain`의 sections·requirements) · 반복 평가 채점(`paseo/live/grade`)
- 코드가 판정하는 것(판정 근거 basis)
  - count: 글자·문장·문단·구간의 수와 길이, 문법 기호(소제목·굵게·물음표)의 개수
  - exact: 계약에 적힌 문자열·구조와의 글자 그대로 일치(구성의 제목·소제목·카드 칸이 초고에 실렸는지, 칸이 채워졌는지)
  - process: 실행 기록(회차·호출 수·완료 여부) · 출력 형식(schema)
- 검토(LLM)가 판정하는 것: 뜻을 읽어야 하는 모든 기준 · 말투·시점의 일관, 과장, 도입 장면, 용어 풀이, 사례가 원칙을 보여 주는지, 사실 근거 · 점검표 `seasoning.CHECKS`의 예/아니오와 근거 표현 인용 · 코드는 그 판정(review)을 집계만 한다
- 금지: 낱말·어미 목록이나 정규식으로 글의 뜻·어조·질을 판정하거나, 그런 값을 판정 근거 지표로 검토에 넘기는 것
- 금지 이유(실측 2026-11-15): 되묻는 문장 "누구나 …할 수 있을까?"가 과장어로 집계 · 호칭 낱말 비율 0을 근거로 검토가 '독자에게 말하지 않음' 판정 · 본문에서 풀이된 용어가 미풀이 후보로 넘어가 미통과 · 낱말은 문맥을 모르고, 검토는 넘겨받은 수치를 근거로 삼는다
- 금지 아님: 형식 토큰화(문장 경계·마크다운 문법) · 사용자 입력의 수량 표현 읽기(분량 `parseLength`, 구조화 입력이 우선) · 프롬프트에 싣는 예시 낱말(작성 안내이고 판정이 아님)
- 확장 절차
  - 새 코드 지표: `METRIC_BASIS`에 count 또는 exact로 등록 · 둘 중 어느 것도 아니면 코드 지표가 아니다
  - 새 채점 기준: `GRADERS`에 basis와 함께 추가 · 뜻 판정이 필요하면 basis는 review뿐
  - 새 의미 기준: `seasoning.CHECKS`에 예/아니오 질문으로 추가 · 근거로 인용할 코드 측정값은 등록된 지표만
- 실패 복구: 검토 판정이 흔들리면 질문을 더 좁은 예/아니오로 나누거나 근거 인용을 요구한다 · 코드 어림으로 되돌리지 않는다 · 판정의 일관성은 `ai:eval`의 점검표 항목별 미통과 횟수로 본다
- 완료 기준: `draftMetrics` 출력 키가 `METRIC_BASIS`와 일치하고 근거가 count·exact뿐 · `GRADERS` 근거가 count·exact·process·review뿐 · 판정 코드에 한글 낱말을 담은 정규식이 허용 목록(문장 경계) 밖에 없음 · `tests/judge-001.test.mjs`
- 한계: 검사는 정규식 리터럴과 등록부를 본다 · 문자열 낱말 목록을 `includes`로 대조하는 식의 우회는 잡지 못하므로 코드 리뷰에서 이 계약으로 거른다
- 관련: ADR-0013 · ADR-0007 · RES-007
